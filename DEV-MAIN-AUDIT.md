# Wholesale Billing: `dev/main` audit

**Audited commit:** `8f0db9de0c9ec69a97fb7533af80c3ca40df4709`. When fetched, `origin/dev/main` was **byte-for-byte the same commit** as the accepted stock-sync checkpoint. There is no newer UI diff between those two references. The frontend and operations router first enter the visible history in the combined snapshot `0f7ffe9c`, so that history cannot tell us which exact changes Antigravity made relative to an earlier Windows-only build. For a visual/code diff of the two versions, supply the clean source or commit of the last UI you liked. This audit compares the current source with the agreed behavior and tests specific defects independently.

**Read-only source review:** no application, branch, GitHub, or shop database changes. Test writes used disposable in-memory PostgreSQL (PGlite) with synthetic records. Python logic checks and build checks ran from a temporary archive. Source line references below are for the audited commit, not the older Arena checkout.

## 1. Stop-ship: money, customer and inventory records

| Finding | Evidence and consequence | Smallest safe fix / acceptance test |
|---|---|---|
| **New settlements can fail before saving anything** | `backend/app/routers/operations.py:23–46, 1741–1758, 1984–2000`. Payment and container routes pass a dict from `model_dump()` to a helper that calls `.encode()` on a string. `Payments.tsx:185–238` always sends operation IDs. I executed the actual helper with a dict and reproduced the `AttributeError` before any settlement write. | Use one canonical payload serialization and one durable operation ID per submitted payment/can movement. Exercise money only, cans only and both through FastAPI with the operation IDs present. |
| **Retry does not reliably protect against duplicate settlement** | `Payments.tsx:185–186, 223–254` makes new IDs each submission and treats a lost response as failure. `Sale.tsx:121–149, 310–330` submits the separate can return without a durable ID. `operations.py:23–81` stores operation keys globally rather than scoped to the authenticated actor and action. | Store operation ID and payload until the result is known. Replay returns that operation’s result only; it must not post again. Add a request-in-flight guard and verify with a response deliberately dropped after commit. |
| **Extra old-debt payment inflates the new invoice’s paid amount** | `operations.py:767–784` passes the new sale ID to `receive_payment` for the old-debt portion. `database/15_customer_accounts.sql:47–59` increments `sales.amount_paid` for every linked payment. PGlite confirmed a Rs. 100 invoice holds `amount_paid = 110` after an extra Rs. 10 is posted this way. The initial API response can still say Rs. 100 paid on the bill, while History reads Rs. 110. | Post the debt portion as an account payment without increasing paid-on-this-bill. Persist the association and split separately, atomically. Verify Rs. 1,700 billed / Rs. 2,000 tendered / Rs. 500 old debt → Rs. 1,700 paid on invoice, Rs. 300 old debt paid, Rs. 200 left, no change, same on reprint. Lock the customer before reading and validating the balance for the split: the current read at lines 630–648 happens before the SQL function takes the customer lock. |
| **A missing/inactive customer can silently become a different customer** | `operations.py:628–644` looks up the requested active customer, then falls back to the first active customer on a valid-but-unknown, archived or missing ID. An expected-balance check can catch some cases but not when balances match. | Reject an invalid customer and keep the draft. If the shop wants walk-in sales, use an explicit walk-in choice. Verify an archived customer cannot post to another account. |
| **Voiding twice can restore the debt twice; corrections do not reliably match history** | `operations.py:1861–1980` updates payment amount in place, posts a ledger delta, and does not lock/check an already-voided payment before applying a reversal. Neither path updates the invoice’s stored paid amount. `Payments.tsx:480–484` sends `payment_method`; `PaymentCorrectionRequest` expects `method_id`, so the method edit is silently ignored. A no-amount method correction also still attempts a zero-value ledger adjustment. | Lock the payment row and record a single auditable reversal/replacement. Make method-only edits use a real supported method and keep the customer ledger, original invoice treatment and reports consistent. Test correction, void, repeated void and simultaneous attempts. |
| **Goods returns over-credit discounted items** | `database/17_cancel_and_return.sql:75–95` credits full unit selling price, ignoring the original invoice discount. PGlite: a Rs. 100 line discounted and paid at Rs. 80 produced a Rs. 100 credit when returned. The same function puts every returned unit back into sellable stock; no condition/disposition is captured. | Allocate returns against the original discount-adjusted value, and distinguish sellable returns from damaged goods. Preserve the ledger and use the shop’s approved refund policy. |
| **Canceling paid invoices changes stock and debt but does not settle cash or cans** | `database/17_cancel_and_return.sql:13–45` restores all sale stock and credits the invoice total, with no payment refund/reversal or container reconciliation. PGlite: canceling a paid Rs. 100 invoice left Rs. 100 in linked receipts, Rs. 100 account credit and one can outstanding. Credit instead of cash may be intentional, but the UI must say so; it cannot assume goods and cans physically returned. | Define paid cancellation, refund/credit and actual goods/can movement explicitly. Until approved and tested, do not present paid cancellation as a complete reversal. |
| **Empty-can returns can target the wrong container SKU** | `operations.py:786–815` issues cans under the sold returnable SKU; `operations.py:1996–2039` picks the first flagged returnable SKU when none is sent, and returns that SKU’s held count. Checkout and Pay / Return do not supply an explicit container type, yet the customer summary sums all types. One type may work; multiple flagged types can reject a valid return or show the wrong count. Returns only move the customer’s container ledger, not physical empty stock. | Use an explicit configured container identity or let the cashier choose when there is more than one. Return per-type and total quantities separately. Define any physical empty-stock posting explicitly to avoid double counting. |
| **Request data still controls sale price and some invalid quantities are silently changed** | `operations.py:689–700, 744–757, 1204–1214` accepts a positive client price instead of obtaining an authoritative price or requiring an authorized override, coerces quantities to at least 1, and passes `allow_over_limit=true` for every checkout. SQL still blocks employee credit overrides, but manager/owner overrides are implicit, not confirmed. | Reject invalid amounts/quantities instead of coercing them. Make price and credit-limit overrides explicit and audited. Use exact money values and test submission after a price or credit-limit change. |

## 2. Stock, customer, history and report integrity

- **Fresh client installs cannot receive stock as shipped.** `database/04_products.sql:12–27` and the install modules do not add `default_buying_price`. `operations.py:1192–1198` references that column inside a SQL `CASE`; PostgreSQL validates column references before evaluating the branch. I installed modules 00–19 and reproduced SQLSTATE `42703` on that query. Product edit also silently skips saving a default cost when the column is absent (`operations.py:532–547`). Supply a reviewed additive migration and verify a separate per-batch cost override. Do not change historic batch costs.
- **Stock identity improvements should be kept.** Latest follow-up keeps product selection and Billing cart keys by `type_id`, clears a disappeared selection, and shows unclaimed real SKUs. However, the starter-card code (`Stock.tsx:374–407`) checks SKU and exact name within the same `find`, so an earlier same-name record can beat the configured SKU. Match canonical SKU first, then use an approved unambiguous fallback if needed. Some stock write endpoints still support legacy index/name fallback (`operations.py:1173–1182, 1269–1278`); require stable identity on mutations after checking supported callers. Batch/movement errors are swallowed and appear as empty history (`Stock.tsx:172–183`).
- **Tamil product names are not persisted.** The Add/Edit modals collect Tamil names and put them into local result objects after saving, but do not send them in the request. The backend translates only hardcoded names. Edit also shows SKU read-only even though the API accepts SKU updates. Persist supported fields or do not offer them as editable. See `AddProductModal.tsx:60–99`, `EditProductModal.tsx:77–104, 157–194`, `operations.py:186–201, 284–296`.
- **Demo customers still appear in real workflows.** Billing and Pay / Return initialize to sample customers and ignore a failed/empty customer lookup. Customers also initializes with sample rows and merges sample fields into real rows. This is particularly misleading during startup or outages on a clean installation. Use distinct loading, empty and error states; no customer should be selected or billable from a fixture. See `Sale.tsx:15–24, 100–116`, `Payments.tsx:19–20, 62–78`, `Customers.tsx:21–22, 41–84`.
- **Customer and invoice lookup limits differ.** `/customers/list` supports search/offset but defaults to 100; Billing and Pay / Return fetch that first page and filter locally. A valid customer outside it can disappear from checkout/settlement search. Reports requests up to 200 invoices and applies its date/status filters locally, without traversing subsequent pages (`Reports.tsx:76–90, 148–163`). Move filtering and pagination to the API while preserving archive isolation.
- **Settlement responses can repaint a different customer’s balance.** `Payments.tsx:95–112, 218–221, 248–251, 608–616` updates whichever customer is currently selected after an async response, even though the request was for the old selection. Changing customers also clears partial-failure state without binding the pending action to the original customer. Apply results only to the matching customer ID; keep pending retry state bound to that account.
- **Invoice History does load line items in this code, but it is not the original receipt.** Immediate preview builds from the cart, uses a client timestamp and hardcodes Cashier (`Sale.tsx:345–382`). History joins current customer/product names, units, phone/address, SKU (`operations.py:929–985`) and does not return original tender/change. The supposed after-sale balance reads ledger entries whose reference ID is the sale UUID, whereas payment ledger entries reference payment UUIDs (`operations.py:1050–1065`, `database/15_customer_accounts.sql:55–59`); it can show the pre-payment balance, or a later cancellation. Persist an immutable checkout snapshot for new invoices where needed; mark legacy unknown values as unavailable instead of inventing them. Use the same saved response for immediate preview and history.
- **A4 PDF is an image sliced at arbitrary page heights.** `PrintInvoiceModal.tsx:33–79` captures the invoice node, downloads directly, and for multi-page A4 shifts the same full image up by 297 mm on each page. This can cut through a row/totals and does not repeat table headings. Print is separate and has hide rules in `index.css:4045–4125`; I did not reproduce the old checkout-print leak here. Verify both formats independently on Windows. The `INV-000037` failure cannot be verified without that environment; the client defaults to `http://localhost:8000` and depends on reachability and CORS/origin setup.
- **Home and Reports can disagree about losses.** `operations.py:2122–2128` exposes signed Home profit for authorized roles, but `:2199–2200` clamps report gross profit to zero. Executing the exact expression shows Rs. 350 sales − Rs. 432 cost → displayed Rs. 0, not −Rs. 82. Returns are counted separately but not applied to summary revenue/COGS. Collection SQL sums all methods, while Home aliases the same figure as cash and total collections. There is no daily ledger movement breakdown as described in the earlier completion report. Agree on a return/cancellation date policy and reconcile one shared calculation; preserve genuine losses. Use one shop timezone: UI invoice filters currently use UTC while dashboard SQL uses `CURRENT_DATE` and report periods use Python `date.today()`.

## 4. Release and verification

- Exact snapshot: `npm ci` failed with missing `@emnapi/core` and `@emnapi/runtime` lock entries under Node 22.22.3 / npm 10.9.8. After `npm install` updated dependencies **in the temporary copy**, `npm run build` succeeded. `tsc --noEmit` still failed on Stepper, invalid icon keys and a missing translation key. A green Vite build does not cover type safety.
- Disposable PGlite: SQL modules 00–19 applied. Reproduced missing buying-cost column, discounted return over-credit, invoice paid amount inflated by linked old debt, and residual credit/receipts/cans on cancellation. Directly checked the settlement helper and report loss expression. These are not claims of Windows or full HTTP end-to-end testing.
- Browser launch in this environment was blocked by a missing Chromium system library (`libnspr4.so`). Screenshots, print/PDF output, scroll fit, and running Windows UI are unverified here. The earlier Stock browser proof remains scoped to Stock as reported by the user.
- The included Stock integration test checks API/DB, not rendered screens. Its test DB URL guard also does not prove the independently configured `TEST_API_URL` serves that same database. Before running write suites, launch a separate API against the isolated DB and verify both endpoints target it.
- `start.bat` still launches Vite dev through npm, expects a prebuilt local Python venv, does not wait for actual readiness or open a browser, and echoes demo PINs. This is not a verified client handover. Keep the clean client DB separate, remove visible test defaults, bundle local assets, and test one-click launch, restart persistence and backup/restore before delivery.

## Recommended order — small commits, no broad redesign

1. **Money and identity first:** settlement pre-write/retry, wrong customer fallback, correct old-debt allocation and repeat void guards. Test database effects, including lost responses. Do not replay unknown live payments.
2. **Stock install and 19 L movement:** add the approved schema change and deterministic container mapping. Keep the accepted Stock/Billing SKU sync. Test a fresh database and multiple can types.
3. **Invoices and reversals:** persisted itemized receipts and tender snapshots, correct return/cancel accounting, print/PDF verified in Windows. Do not rewrite legacy invoices to make tests pass.
4. **Reports and UI:** shared reconciled aggregates; remove demo data, restore the step indicator, then compare actual screens against the last approved UI in English and Tamil. Preserve Home’s four cards, daily strip and sidebar.
5. **Client release:** reproducible install/build, no demo records or credentials, stable offline launcher, tested backup/restore. Each batch needs a small regression check and approval before continuing.
